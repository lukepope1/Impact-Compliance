# Deploying a review environment (Render)

For getting the platform in front of reviewers on a shareable URL. This is a **demo
environment with seeded dummy data**, not a production deployment — see
[What this is not](#what-this-is-not) before pointing anything real at it.

## How it's shaped

**One web service, not two.** The Express server serves the built client from the same
origin as the API. That isn't just about cost: the client calls the API on relative
`/api/...` paths, so same-origin serving means no CORS to configure, no API base URL baked
into the client build, and no way for the two halves to drift onto different versions of
each other.

`server/src/index.ts` mounts the client build only when `client/dist` exists, so local dev
— where Vite serves the client on its own port — is untouched. Anything that isn't
`/api/*` returns `index.html` so client-side routes and refreshes resolve instead of 404ing.

## Deploying

1. Push the repo to GitHub (already done).
2. In Render: **New → Blueprint**, point it at the repo. It reads `render.yaml` and creates
   both the web service and a free Postgres database.
3. Deploy. First build takes a few minutes.
4. Open the `*.onrender.com` URL Render gives you. **No custom domain is needed** — you
   only need one if you want a branded URL.

Everything else is already configured in `render.yaml`: `DATABASE_URL` is wired from the
database, `JWT_SECRET` is generated by Render (the server refuses to boot on a weak one),
and the demo data seeds itself on first boot.

### What happens on each boot

`server/scripts/start-production.mjs` runs before the server listens:

1. `prisma migrate deploy` — applies existing migrations only. Unlike `migrate dev` it
   never generates or resets anything, which is what you want running unattended against a
   live database. It runs at start rather than at build because a Render build has no
   database attached.
2. Seeds, if `SEED_ON_START=true`. The seed no-ops when the data is already there, so
   leaving the flag on across restarts is safe.
3. Starts the API and serves the client.

## Signing in

The login page has one-click buttons for each portal — Impact, QALICB, CDE. Reviewers
click a role and they're in; there's nothing to type and no accounts to hand out.

These perform a **real login** against the seeded accounts (all using `password123`), not
a header switch, so what reviewers see is exactly what those roles really see — including
the places where a portal is correctly denied access to something.

`render.yaml` raises `LOGIN_RATE_LIMIT` to 500. The strict production default of 10 per 15
minutes is keyed by IP, so a team sharing one office network would lock each other out
within minutes of clicking between demo accounts — precisely the pattern the limiter
exists to stop.

## Known limits of this environment

Worth telling reviewers up front, so they report real problems rather than these:

- **Uploaded files disappear on redeploy.** Render's free disk is ephemeral. Evidence
  uploaded during a review won't survive the next deploy. Set `EVIDENCE_S3_BUCKET` +
  `AWS_REGION` (see `docs/AWS_SETUP.md`) if uploads need to persist.
- **Uploaded files can't be downloaded.** With no `CLAMAV_HOST` configured, uploads stay
  `pending` and downloads are refused. That's the fail-closed behaviour working as
  designed (`docs/MALWARE_SCANNING.md`), but it looks like a bug if nobody warned you.
- **Email notifications aren't delivered** unless SMTP is configured. In-app notifications
  still work; email rows just record as failed.
- **The free database sleeps** after inactivity and expires after 90 days on Render's free
  tier. The first request after a sleep is slow.
- **The free web service spins down** when idle, so the first visit after a quiet period
  takes 30–60 seconds to respond.

## What this is not

**The URL is public and one click gets anyone in.** There's no gate in front of the demo
account buttons — that's the point of them, but it means anyone with the link has full
access to whatever is in that database. Keep it to seeded dummy data.

Before this carried anything real it would need, at minimum: a real identity provider
replacing the interim local-credential login, the demo account buttons removed, S3 for
evidence, a malware scanner, and a paid database with backups. See the
"Before this could go anywhere near production" section of `docs/PHASED_PLAN.md`.

## Testing the production build locally

The same path Render takes, minus Render:

```bash
npm run build --prefix server
npm run build --prefix client
cd server && SEED_ON_START=true npm run start:production
```

Then open `http://localhost:4100` — the client is served by the API server, same as in the
deployed environment.
